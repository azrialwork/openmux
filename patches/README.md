# Patches

This directory holds the entire delta that `openmux` carries on top
of the upstream baseline pinned in `../upstream.json`.

## Rules

- One logical change per patch file.
- Files are named `NNNN-short-description.patch`, numbered in apply
  order (`0001-...`, `0002-...`, ...).
- `series` lists the patch filenames in apply order, one per line.
  Lines starting with `#` and blank lines are ignored.
- Every patch is listed in the table below with what it does and why.
- Preferred format: `git format-patch` output against the pinned
  baseline commit, so authorship and the commit message survive.
- A patch that no longer applies cleanly on the pinned baseline
  fails CI — fix the patch, never the baseline pin, to resolve it.

| `0006-remove-per-model-system-prompts.patch` | Deletes the six per-model system prompt files in `packages/core/src/plugin/system-prompt/` (`anthropic.txt`, `gpt.txt`, `gpt-astra.txt`, `kimi.txt`, `meta.txt`, `trinity.txt`) and the built-in prompt plugins in `packages/core/src/plugin/optimize.ts` that selected them by model id (gpt/gpt-astra, claude, kimi, trinity, muse), including their registration in the builtin plugin list. | `0007-restructure-built-in-tool-descriptions.patch` | Restructures the top-level description of every built-in tool into one consistent, scannable form — an opening line stating what the tool does, a structured details section carrying every fact, rule and limit of the original (all of them preserved, plus code-grounded detail such as real defaults and failure behaviour), and a closing `Batching:` section stating the tool's batch/parallel call priority. The batching guidance is grounded in the runner's actual execution model: the session runner forks each tool call in a step into its own fiber and runs the block's calls concurrently (`packages/core/src/session/runner/step.ts`), file mutations serialize their read-modify-write under a per-path lock (`FileMutation.withLock`, so parallel calls are safe across different files but must be sequenced for the same file), reads take no locks, `todowrite` replaces whole state (one call per block), and `question` batches through its own `questions` array. Covers the inline descriptions in `packages/core/src/tool/plugin/*.ts` (edit, read, write, glob, grep, shell, skill, subagent, question, webfetch, websearch, experimental_image_generate, the artifact, MCP-resource, session/worktree/models and schedule tools), the two external description files `packages/core/src/tool/patch.txt` and `packages/core/src/tool/todowrite.txt` (in patch.txt the envelope format, headers and example are preserved byte-for-byte), the `opencode` namespace description, and the Code Mode `execute` tool description in `packages/core/src/codemode/tool.ts`. Total description text grows from 9,891 to 24,828 characters (+151%) — growth was explicitly allowed. No tool logic, names, parameters, schemas or per-parameter descriptions change; `artifact_create`'s provider-rendered description is untouched; the one test that asserts a description verbatim (`tool-execute.test.ts`) was updated to the new text. | Boss's fourth patch decision, revised (superseding the earlier tighten-only direction): tool descriptions should be more structured, more detailed and clearer while remaining strictly factual, and every description must state the tool's batch/parallel priority so OpenCode's parallel tool execution is used to best effect. |
| `0008-agent-system-prompts-and-code-permissions.patch` | Gives each primary and subagent agent its own system prompt as a `.txt` file in `packages/core/src/plugin/agent-prompt/` (`build.txt`, `plan.txt`, `general.txt`, `explore.txt`), imported by `packages/core/src/plugin/agent.ts` and `packages/core/src/plugin/plan.ts`; Explore's prompt moves out of its inline const into `explore.txt`. Because an agent system prompt replaces the base `system.txt` wholesale (including the tool-guidance bullets), each prompt is self-sufficient: structured, detailed, and strictly factual, carrying the harness, communication, and tool-use guidance itself. The two primary agents' prompts prioritise the delegation system — Explore for read-only codebase exploration, General for parallel multi-step and research work, batched in one block, with the primary staying responsible for synthesis and verification. Permissions are tightened in code in the same patch: Plan gains denies for `shell`, `subagent` on `*` with an allow for `explore` only (the subagent resource is the agent id), `experimental_image_generate`, `worktree_create`, the `schedule_create`/`pause`/`resume`/`delete` mutations, and the `artifact_create`/`update`/`delete` mutations — closing every write path that bypassed its existing `edit` deny (which already covers edit/write/patch through the shared `edit` action). Explore loses its `shell` allow, so its leading deny-all governs shell: read-only shell is not expressible in the rule system because the shell resource is the command's literal text including redirects, making prefix allowlists leaky. Build's and General's permission rules are unchanged — research showed they already encode their roles (Build is the unrestricted executor; General's question and subagent denies are its role boundaries). The hidden agents (Compaction, Title, Summary) are untouched, and user config agents keep overriding the built-ins, since the config agent plugin still runs after them and overwrites `system`/appends rules. Tests asserting the old shapes (Build without a system, Explore with shell allowed) were updated, and Plan's new denies are covered by a dedicated test. | Boss's fifth patch decision: each primary and subagent agent gets its own structured, factual system prompt file; primary agents prioritise delegation to subagents; and each agent's role is enforced by its written permission rules in code, not by prompt text alone. |
| `0009-enforce-delegation-and-tool-appropriateness-in-code.patch` | Enforces delegation and tool appropriateness in code for the built-in agents. Build and General gain per-segment shell hygiene denies in `packages/core/src/plugin/agent.ts` (`cat`/`head`/`tail`/`less`/`more`, `ls`/`find`/`tree`, `grep`/`rg`/`ag`/`ack`, `sed -i`/`sed --in-place`, and `echo`/`printf` output redirection): the shell tool asserts permission per parsed command segment, so a denied segment blocks the whole compound command, and reading, finding, searching, and in-place editing are forced onto the dedicated `read`/`glob`/`grep`/`edit`/`write` tools. Build (in `agent.ts`) and Plan (in `packages/core/src/plugin/plan.ts`) additionally gain whole-tool `glob` and `grep` denies, which remove both tools from their catalogs and Code Mode inventories entirely — all discovery goes through the Explore subagent, and the primaries keep `read` for files whose path is already known. A new internal plugin, `packages/core/src/plugin/tool-policy.ts` (registered in `internal.ts`), adds what permissions cannot express: a per-user-turn exploration budget for Build and Plan that counts only COMPLETED direct `read`/`glob`/`grep` calls (a failed call returns its allowance; a model-visible `Tool.Error` remains only as an anti-overshoot backstop for parallel blocks that share one request) — 4 free calls, an ephemeral `[system-reminder]` delegation reminder spliced into the next request at the 5th completed call (via the session `context` hook, goal-plugin style, never persisted), and at 8 completed calls a delegation mode in which the context hook removes every tool except `subagent` and `question` from the request's tool list (state-driven and re-evaluated on every request, so the full set returns by itself after a refill or a new turn) and prefixes the `subagent` tool's description with the required next action. The budget refills on a new user turn (harness synthetics and compaction checkpoints do not count as user turns) or on a completed, substantive delegation: the target must be Explore (General also qualifies, but only for Build), the briefing must be at least 40 characters, and the child must actually finish with a non-empty result — a foreground delegation settles in the tool `execute.after` hook once the child completes, a background one only when its `<subagent state="completed">` synthetic lands in the parent transcript; a launched, failed, empty, or trivial delegation refills nothing. Build and Plan also gain a `steps = 100` ceiling in their agent definitions (`agent.ts`, `plan.ts`) as a runaway-loop backstop. The same plugin rewrites hygiene-caused shell `BlockedError`s for Build and General into guidance naming the designated tool, following plan.ts's rewrite precedent. The `build.txt`, `plan.txt`, and `general.txt` prompts are updated to state the enforced facts. New tests cover permission evaluation over real `ShellParse` segments, real Tool registry catalog snapshots, the budget ladder (completed-only counting, in-flight slot reservation and return on error), delegation-mode tool removal and restoration, foreground and background refill settlement, the steps ceiling, and the guidance rewrite; the exact-ruleset assertions in `config/agent.test.ts` and the compaction assertion in `agent.test.ts` were updated to the new shape. | Boss's sixth patch decision, in the strictest of the three designed scopes (Opsi C — pagar penuh): the v0.6.1 TUI test drive proved patch 0008's prompt-level delegation and tool-choice guidance is ignored by the model (Build explored via shell and never delegated, while code-enforced Plan permissions worked exactly as designed), so both behaviours are now enforced in code — no favourite tool, and delegation backed by a hard budget fence. The anti-stubbornness hardening designed afterwards — delegation mode instead of a block message a model can argue with, completion-based refill with a substance floor, completed-only counting, and the steps ceiling — was folded into this same patch at Boss's instruction before its first push. |
